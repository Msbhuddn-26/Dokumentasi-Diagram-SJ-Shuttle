Dashboard Use Case Activity Sequence Flowchart
Activity 01

Login & Validasi Status SIAKAD

Proses autentikasi dimulai ketika pengguna (penumpang atau sopir) membuka layar aplikasi, memasukkan kredensial berupa NIM atau Email beserta kata sandi, dan menekan tombol masuk. Sistem SJ Shuttle kemudian menerima dan mengenkripsi data tersebut untuk dilakukan cross-check ke database internal. Apabila kredensial tidak valid, sistem secara otomatis menolak akses dan menampilkan pesan error. Namun, jika kredensial valid, sistem akan memanggil API SIAKAD; jika merespons, sistem akan mengunduh meta-data status mahasiswa, menerbitkan Token Akses, dan mengarahkan pengguna ke halaman Dashboard. Jika API SIAKAD sedang bermasalah, sistem akan menampilkan notifikasi kegagalan sinkronisasi.

Activity 02

Top-Up E-Wallet (Integrasi Midtrans)

Alur pengisian saldo diawali oleh penumpang yang membuka menu dompet digital, memasukkan nominal top-up (minimal Rp 10.000), dan menekan tombol isi saldo. Sistem memvalidasi nominal tersebut lalu mengirimkan request ke server Midtrans, yang kemudian mengembalikan Snap Token untuk memunculkan jendela pembayaran. Penumpang dapat membatalkan proses atau melanjutkannya dengan menyelesaikan transfer. Midtrans mengecek kesesuaian nominal transfer; jika sesuai, Midtrans mengirimkan Webhook berstatus Settlement ke sistem SJ Shuttle. Sistem memverifikasi keaslian signature, menyuntikkan nominal ke saldo wallet, menerbitkan log kredit, dan diakhiri dengan pengiriman push notification.

Activity 03

Generate Dynamic QR Token

Penumpang menekan tombol "Bayar Tiket", memicu sistem untuk mengecek status akademik mahasiswa. Bagi mahasiswa reguler, sistem mengecek saldo berjalan; jika di bawah Rp 7.500, proses diblokir dan muncul peringatan. Bagi mahasiswa kelas karyawan (CK/CS), pengecekan limit saldo ini diabaikan. Sistem selanjutnya mengkalkulasi UUID acak, menetapkan kedaluwarsa 5 menit, dan merender QR Code berbingkai Emas atau Abu-abu di layar ponsel. Jika batas waktu habis sebelum dipindai, sistem secara otomatis menghanguskan QR lama dan me-refresh layar.

Activity 04

Pemindaian Tiket & Geo-Validation

Pengemudi mengarahkan kamera untuk memindai QR Token milik penumpang. Sistem mengekstraksi UUID dan mengecek limit sisa kursi; jika penuh, transaksi ditolak. Jika kursi tersedia, sistem mengambil koordinat GPS absolut dari kedua perangkat untuk dikalkulasi jarak trigonometrinya (Haversine). Jika jarak terpaut lebih dari 15 meter, sistem menolak transaksi (Indikasi Fake GPS). Sebaliknya, jika jarak valid, sistem mengeksekusi Lock-For-Update pada database, memotong saldo sebesar Rp 0 atau Rp 7.500, mencatat mutasi, mengurangi kuota kursi, membunyikan suara validasi di HP pengemudi, dan mengubah layar HP penumpang menjadi warna hijau (LUNAS).

Activity 05

Protokol Fallback Scanner (Darurat)

Sebagai mitigasi jika HP penumpang mati, pengemudi menekan tombol "Mode Darurat", meminta KTM fisik, dan memindai barcode KTM atau mengetikkan NIM. Sistem mencari data mahasiswa tersebut di pangkalan data offline (Cache). Jika identitas tidak dikenali, sistem menolak input manual. Namun jika ditemukan, pengemudi mengonfirmasi masuknya penumpang, dan sistem mencatat status Pending Deduction ke dalam antrean. Sistem akan mengeksekusi sinkronisasi dan memotong saldo secara tertunda begitu HP penumpang kembali online.

Activity 06

Kirim Peringatan Kedaruratan (SOS Alert)

Dalam kondisi krisis, pengemudi membuka panel menu SOS, mendapat peringatan konfirmasi, lalu menggeser slider darurat. Jika koneksi internet tidak stabil, payload SOS disimpan secara lokal dan sistem melakukan proses retry pemancaran bertubi-tubi hingga sinyal terkirim. Jika koneksi stabil, sistem seketika merubah status armada di database menjadi OFFLINE-DARURAT dan membekukan fungsi QR Scanner. Secara serentak, peringatan ini masuk ke Web Dashboard Dispatcher yang langsung memicu alarm audio dan memunculkan indikator merah berkedip pada peta.

Activity 07

Otomatisasi Mode Hibernasi Siang

Auto-Scheduler (Cron Job) yang memantau waktu peladen mendeteksi pukul 10:00 WIB dan memicu fungsi Sleep di latar belakang. Sistem SJ Shuttle merespons dengan memutus secara paksa seluruh koneksi WebSockets pengemudi, menghentikan penerimaan transmisi GPS, dan mengubah label pelacakan menjadi "Armada Istirahat". Sistem kemudian berdiam hingga mendeteksi pukul 15:30 WIB, lalu memicu fungsi Wake-Up. Sistem membuka kembali port WebSocket, menginstruksikan pengemudi untuk kembali mengirimkan GPS, dan sistem dinyatakan siap melayani antrean boarding sore.
